TRUST-BUT-VERIFY: PROJECT BRIEF

Post-quantum zero-trust messaging and explainable audit detection
Track: Security, Systems & Post-Quantum Defense  |  Reference implementation for a hackathon submission  |  Demo video: pending (human-supplied; shot list in docs/DEMO_VIDEO.md)

1. What this submission is

A Python 3.11 reference implementation of an end-to-end protected messaging path with post-quantum key establishment and signatures, authenticated envelopes, a durable identity/key lifecycle, a tamper-evident audit log, and a deterministic rule-based detector. It is a sandbox/reference system, not a production deployment.

  • Confidentiality and authenticity: ML-KEM-768 key encapsulation, ML-DSA-65 signatures, AES-256-GCM with an HMAC-SHA256 key-commitment tag, and HKDF-SHA256 derivation.
  • Recipient/device binding and replay defence: all routing metadata is in the AEAD AAD; duplicate message IDs are rejected by a persistent replay cache.
  • Identity lifecycle: signed rotation cutoffs with a grace period, authenticated revocation with cross-node propagation, and owner-or-admin-authorized enrollment/recovery.
  • Audit and detection: SHA-256 hash-chained JSONL audit log, ML-DSA-signed checkpoints, out-of-band anchors, and a deterministic detector with per-alert identity/service/event context.

2. Architecture

Crypto layer

src/crypto: envelope seal/open, AEAD, replay cache, handshake, chunked delivery, resumption. Primitives come from pqcrypto (liboqs-backed ML-KEM/ML-DSA) and cryptography; no custom cryptography is implemented.

Identity and key authority

src/identity_keys: FastAPI service, SQLAlchemy/Alembic schema, enrollment, rotation cutoffs, revocation, re-enrollment, backup, and rate limits.

Audit and detector

src/audit and src/detector: chained audit logging with signed checkpoints and an operator verifier; deterministic rule and graph checks with clock-skew buffering.

Sandbox and CLI

demo/node and src/cli.py: multi-node HTTP sandbox, operator CLI, reproducible demos, and the judge walkthrough.

4. Scope and non-goals

  • No formal verification and no claim of production readiness.
  • No AI/ML detector; the detector is deterministic and rule-based.
  • Keys are generated in process and the sandbox uses an environment-supplied wrap key and HMAC cluster secret instead of an external KMS/HSM.
  • The audit chain detects edits when compared with a trusted head or signed checkpoint; an attacker who can replace the entire log and its checkpoint key can forge a new chain.

THREAT MODEL & SECURITY SPECIFICATION

STRIDE-oriented adversary and control matrix

1. Adversaries considered

  • Network attacker: observes, drops, reorders, replays, or tampers with messages. Mitigation: AEAD, ML-DSA signatures, recipient binding, replay cache, chunk authentication.
  • Future quantum adversary (harvest-now-decrypt-later): Mitigation: ML-KEM-768 and ML-DSA-65; ephemeral session keys provide forward secrecy for completed sessions.
  • Compromised node or malicious insider: attempts unauthorized privilege use, lateral movement, or audit tampering. Mitigation: service-DAG policy checks, role barriers, hash-chained audit entries, signed checkpoints, and out-of-band anchors.
  • Stolen device or key: Mitigation: signed revocation, cross-node propagation, stale-state fail-closed authorization, and owner-or-admin re-enrollment.
  • Operator error / crash: Mitigation: fsynced write-ahead log, authenticated backups, atomic rotation cutoffs.

3. Reliability and recovery

  • Mid-operation crash: the write-ahead log discards torn writes and replays only complete, checksummed entries.
  • Damaged backup: HMAC-SHA3-512 authentication rejects tampered or truncated snapshots.
  • Clock skew: the arrival buffer tolerates ±2000 ms and flags larger skew instead of silently dropping evidence.
