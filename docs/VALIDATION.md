# Validation Guide

This document explains how the repository is validated, what the gates prove,
and what they deliberately do **not** prove. It is the entry point for a
reviewer who wants to reproduce the claims in `README.md`,
`docs/FIX_LEDGER.md`, and `docs/MEASUREMENTS.md`.

## 1. What is validated

The automated suite exercises the shipped code paths, not a parallel
reimplementation:

| Area | Primary tests | What is checked |
| :--- | :--- | :--- |
| ML-KEM-768 / ML-DSA-65 / HKDF | `tests/test_crypto.py`, `tests/test_pqc_hardening.py` | Known-answer and round-trip behavior, malformed inputs, exact interop for `protected_read` |
| Envelope seal/open | `tests/test_integration_e2e.py`, `tests/test_replay_binding.py` | AEAD, recipient binding, replay rejection, signature verification |
| Key lifecycle & rotation | `tests/test_part2_rotation.py`, `tests/test_fix02_rotation_durability.py`, `tests/test_fix01_signed_cutoff.py` | Grace windows, signed cutoffs, crash recovery, post-cutoff rejection |
| Revocation & re-enrollment | `tests/test_part3_revocation_reenroll.py`, `tests/test_fix07_revocation_heartbeat.py` | Cross-node convergence, rate limits, scrypt recovery codes, admin approval |
| Backup / restore | `tests/test_part4_backup.py`, `tests/test_fix05_backup_mldsa.py` | ML-DSA manifest authentication, tamper rejection, rollback protection |
| Audit chain | `tests/test_fix06_cli_log_verification.py`, `tests/test_track4_service_hardening.py` | Hash-chain verification, signed checkpoints, anchor advance, UTC timestamps |
| Detector rules | `tests/test_fix08_change_ticket.py`, `tests/test_fix09_lateral_velocity.py`, `tests/test_fix10_clock_watermark.py`, `tests/test_alert_contract.py` | Explainable rules, change windows, velocity, clock watermark, `event_id`/`services[]` contract |
| Track 4 adapter | `tests/test_crypto.py`, `tests/test_forgery_and_inedge_detection.py`, `tests/test_negative_and_fuzz.py` | `setup`/`read`/`revoke`/`audit`/`protected_read`, whole-state forgery, fuzzed inputs |
| Identity API | `tests/test_phase2_authz.py`, `tests/test_phase3_multinode.py`, `tests/test_readyz_and_rate_limits.py` | Enrollment authorization, actor binding, fail-closed authz, readiness, rate limits |
| Demo node | `tests/test_demo_identity.py`, `tests/test_alert_contract.py` | Fail-closed unknown senders, alert contract, no default keys |
| Packaging & CI | `tests/test_clean_machine_setup.py`, `tests/test_ci_contract.py`, `tests/test_compose_hardening.py` | `.venv` setup, pinned gate tools, CI matrix, compose hardening |
| Docs | `tests/test_docs_drift.py`, `tests/test_benchmark_methodology.py` | No dead URLs, endpoints match code, generated numbers are not hand-edited |

## 2. Environment

Pinned versions are in `requirements.txt` and `requirements-dev.txt`.
The validated interpreter is Python 3.11 (3.11.16 at the time of the recorded
measurements). Node.js is required for the demo/Node bridge; measurements were
recorded with Node v26.13.1. Hardware and OS provenance are in
`docs/MEASUREMENTS.md`.

```bash
make setup     # creates .venv with python3.11, installs pinned deps, enables hooks
```

## 3. Gate commands

```bash
make gates     # ruff + mypy + `python -m src.cli verify-logs` + `pytest . -q`
make demo      # deterministic 6-scene walkthrough used for the video
make bench     # regenerates reports/measurements.json and docs/MEASUREMENTS.md
make brief     # regenerates docs/project_brief.html and .pdf
```

`make gates` is the authoritative gate. CI runs the same commands on Linux and
macOS with Python 3.11 (`.github/workflows/ci.yml`) and also validates
`docker compose config` with throwaway generated secrets.

The current pass count is recorded in `docs/FIX_LEDGER.md`; it is intentionally
not duplicated here so the two documents cannot drift.

## 4. Negative, fuzz, and adversarial coverage

- `tests/test_negative_and_fuzz.py` uses a fixed-seed RNG to mutate base64,
  canonical JSON, audit hashes, challenge/key boundaries, and adapter requests.
- `tests/test_forgery_and_inedge_detection.py` replaces whole state/log files
  and confirms the adapter rejects the forgery.
- `tests/test_replay_binding.py` covers replay and recipient swaps, and
  `tests/test_fix11_delivery_hardening.py` covers chunked-delivery hardening.
- `tests/test_alert_contract.py` asserts every alert is traceable to an
  `event_id` and names its `services`.

## 5. Measurements

`docs/MEASUREMENTS.md` and `reports/measurements.json` are generated by
`scripts/benchmark.py`. They state the scope and limitations explicitly:
single-host in-process microbenchmarks, coarse p99, per-run spread, synthetic-only
detector accuracy, and no confidence intervals. Do not quote those numbers as
production capacity without re-running on the target host.

## 6. Manual and human validation

- `make demo` must exit 0 and print `WALKTHROUGH DEMO COMPLETED SUCCESSFULLY`.
- The 5-minute demo video is human-recorded; see `docs/DEMO_VIDEO.md`.
  `DEMO_VIDEO_URL` stays empty and artifacts render "video pending" until the
  recording is uploaded.
- A human must confirm the judge environment and deadline before submission.

## 7. What is **not** validated

- **Production scale / load.** No sustained multi-tenant load, soak, or
  failover test is claimed.
- **Real network partitions.** Revocation timing uses `TestClient` + SQLite on
  one host, not a real multi-host network.
- **PostgreSQL runtime.** The schema is migration-tested on SQLite; Docker is
  not installed on the recording host, so `docker compose up` was not run here.
  The compose contract is checked statically and in CI.
- **HSM/KMS.** The wrap master key is supplied through the environment; no
  hardware-backed key store is integrated.
- **Real-world detector accuracy.** The labelled detector set is synthetic and
  hand-built; F1=1.00 on it is not a production claim.
- **Independent security audit.** The threat model and code review are
  documented, but no third-party audit is claimed.
